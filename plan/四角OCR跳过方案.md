# 四角 OCR 跳过（像素启发 → Tesseract 确认）方案

状态：**规划中，未动任何源码**。本文件只写设计、数字与验收判据。

## 0. 目标与口径（他定的三条）

1. 启动时扫**固定区域**，认出「跳过」就**点坐标**。
2. 两段式：**像素启发筛候选**，只对候选跑 OCR。
3. **全程离线**：Tesseract，零 Google 依赖（ML Kit 因遥测与 GMS 关系被否）。
4. 区域：**四角比例区 + 命中自学习**。

## 1. 已实测的底座数字（本机 RMX5200 / A17 / KernelSU）

| 项 | 值 | 证据 |
|---|---|---|
| `screencap` 裸帧 | 159–197 ms/帧 | 设备侧 `toybox time screencap` |
| `su -c screencap > /dev/null` | 3 轮 0.628 s ⇒ **210 ms/轮** | 同上（shell uid 起 su；应用域未测，见 §7-T1） |
| `screencap -p`（PNG） | 0.96–1.10 s | **不用**，编码占 5 倍 |
| 裸帧格式 | 头 16 B = `w h format flags` = `1080 2352 1 2`，随后 BGRA8888，全帧 10,160,656 B | `od -An -t d4 -N 16 /sdcard/x.raw` |
| 截图能拍到广告内容 | **成立**：`r4b.raw` 裁出的弹窗卡片里广告创意完整可见 | 已裁图目视 |
| 10 s 窗口可扫轮数 | ≈ 47 | 10000/210 |

## 2. 形态事实（决定为什么要 OCR）

- byfen 是聚合广告：`app_adnet` / `pangle_com.byted.live.lite` / `kwad_ex` / `ksad_dynamic` / `app_webview` / `com.android.gdt.qone.sdk.QoneSDK`。
- 我 10 次冷启动 × 2 采样 = 20 帧，无障碍树 **非空 text 出现 0 次**；形态分布：`ad_view` 空容器 7 帧、`idIvClose` 弹窗 12 帧、进首页 1 帧。
- 他另两张图（18:16、右上角 `5 | 跳过` 胶囊）对应引擎 **已 hit** 的形态：
  `21:47:16.585 hit kind=KEYWORD node=4 | 跳过 dt=134ms`。
- 结论：**至少存在两类纯绘制形态**（弹窗底部 X、四角胶囊），其中弹窗 X 有节点（`idIvClose`），四角胶囊是否有节点**未证**（被中断的那轮取证就是为答这个问题）。

## 3. 包体账（当前 R8 装机件 2,537,761 B）

| 组成 | 只留 arm64-v8a | 三 ABI |
|---|---|---|
| libtesseract + leptonica + jpeg/png/gif | 8–12 MB | 20–30 MB |
| `chi_sim.fast.traineddata`（legacy） | ≈ 2.4 MB | 同 |
| `chi_sim.traineddata`（standard LSTM） | ≈ 10 MB | 同 |
| **合计（64 位机、单 ABI + fast）** | **≈ 11–15 MB** | 30–40 MB |

- 验收机是 arm64 单 ABI，**建议 abiFilters 只留 arm64-v8a**，否则白涨 2–3 倍。
- 这是全案最贵的代价：包体从 2.5 MB → 约 12 MB（≈ ×4.7）。要么接受，要么走 §8 的降级路线。


## 5. 每轮流水线（预算 210 ms 采集 + ~15 ms 本地）

1. **区域**：按 `W,H` 算四角，默认每角 **`0.40W × 0.12H`**，顶边下移状态栏高度（本机 appBounds top=103）。
   宽度不是拍的：参考图（826 px 宽映射到 1080）里 `5 | 跳过` 胶囊占 x≈715–865、y≈265–330，
   而 `0.30W` 的右上角从 x=756 起，**会把胶囊左半边切掉**——切开的候选贴块边，被第 4 步的过滤丢掉，
   整条四角扫描就永远扫不到它。`0.40W` 起于 x=648，左右各留 ≥67 px 余量。
2. **取块**：优先设备侧 `dd skip=… bs=4320 count=…` 逐角只吐 117 KB（四角 468 KB，省掉 10 MB 回读）；dd 语义不稳则退化为整帧读入本地裁。
3. **背景估计**：取块外环 1 圈像素中位数 → `bg`。
4. **候选**：`|lum(p) − lum(bg)| > 45` 二值化，4-邻域连通域；过滤条件：
   - 面积 ∈ [0.5%, 8%] × 块面积（本机 0.40W×0.12H ≈ 207,360 px ⇒ 1037–16589 px；
     参考图胶囊 150×65 的外框 9750、按胶囊填充率 ~0.78 实占 ≈7600，落在区间内）
   - 长宽比 ∈ [1.6, 6.0]（胶囊横排，参考图实测 ≈2.3）或 [0.7, 1.4]（方形角标）
   - **候选必须完整包含在块内**（贴块边 = 被切开的假候选，直接丢）
5. **OCR 确认**：候选框外扩 8 px、2× 最近邻放大后喂 Tesseract，`pageseg=7`（单行）；
   识别串走 `compactText` + `keywordNeedles` 同一套归一，命中 `跳过/skip/跳過` 才算。
   **每帧最多确认 3 个候选**（按"与背景亮度差 × 长宽比接近度"排序）。
   这条上限是必需的：广告创意本身是花图，右上角区域里 `|lum−bg|>45` 的连通域
   在一帧里可能出 5–20 个（参考图右上角就有橙色字与白色卡片），不设上限则
   "只对候选跑 OCR"的省法不成立——OCR 会退化成每帧全区域跑，150–400 ms × N 直接吃满 210 ms 预算。
   候选数分布要在 T2 一并量出来（见 §7-T2）。
6. **点击**：`gestureTap(cx, cy)`。注意现有手势取点偏下
   （[SkipTask.kt:153-156](../app/src/main/java/com/v5yn133n3/skp/engine/SkipTask.kt) 用 `(centerY+bottom)/2`），
   OCR 路线**必须用真中心**，不复用这个偏移。
7. **延迟**：沿用 `nap()` 的 50–350 ms 随机（他钉过的界，不动）。

## 6. 自学习

- 命中后写 `{pkg: {box, w, h, hits, misses, ts}}` 到 `skip.corners.xml`。
- 下次启动：**先只扫已学框**，1 帧不中即回落到四角全扫。
- 失效条件：`w/h` 与当前屏幕不符、连续 3 次未命中、30 天未使用 → 删除条目。
- 学习数据**不进** `skip.rules.xml`，避免污染用户可见规则与内置合并逻辑。

## 7. 前置验证（写代码之前必须过，过不了整案改向）

- **T1** 应用域（非 adb shell）起 `su -c screencap` 的真实单轮耗时与稳定性。adb shell 域测得 210 ms，应用域 su 可能更慢或被 KernelSU 限流。
- **T2** **Tesseract 对 `5 | 跳过` 这种"数字 + 竖线 + 中文"的识别率**。拿他这张 18:16 截图裁右上角做金标准，`chi_sim.fast` 与 `chi_sim` 各跑 20 次，记召回与耗时。召回 < 90% 则 OCR 白名单要放宽到"含 跳过 或 含 |数字| 形状"，或改走 §8。
  同轮量两件事：① 花图背景上"每帧候选数"的分布（决定 §5 的每帧 3 个上限够不够、会不会把真候选挤掉）；
  ② 阈值 `|lum−bg|>45` 在**深底白字**（参考图那种深灰胶囊在浅底上）与**浅底深字**两个方向是否都能过——
  我上一轮就是拿 `lum>200` 的单向阈值把深灰胶囊整个漏掉的（见 §11）。
- **T3** 四角形态到底有没有无障碍节点（被中断的那轮取证）。**若节点存在，OCR 对 byfen 就是多余的**，只做 `popup_rules`/keywords 即可。
- **T4** 部分广告窗口可能带 `FLAG_SECURE`，`screencap` 会拍到黑帧。需按包探测并在 UI 上说明"该 app 不支持"。

## 8. 降级路线（T2/T3 不过时）

只保留像素启发 + 自学习，不引 Tesseract：包体 +0，四角定位靠"非背景胶囊 + 长宽比"，
点中心。代价是**无法区分「跳过」和「了解详情」**，必须靠"位置在角上 + 面积小 + 有倒计时变化"
三重约束兜，误点风险显著高于 OCR。

## 9. 风险清单

| 风险 | 说明 | 缓解 |
|---|---|---|
| 误点广告 | 候选判错就是"点进去"，比不点更糟 | 只认 OCR 白名单词；首次命中只学不点（可配） |
| 能力分层 | 纯无障碍档无截图，功能永久不可用 | 开关置灰 + 文案写明"需 Root/Shizuku" |
| 功耗 | 47 帧/10 s 的截图+合成 | 命中即停；自学习后单框单帧 |
| R8 | `isMinifyEnabled=true`，Tesseract Java 层需 keep | 加 `proguard-rules.pro` keep，且装机后实跑一次识别 |
| 取证目录 | `evidence_device/` 下新建子目录会被静默删除（本轮发生 2 次） | 证据先落设备 `/sdcard/`，本地写 `/tmp` |

## 11. 我此前判错、已推翻的三条

1. 亮块检测用 `lum > 200`，而实际胶囊是**浅底上的深灰胶囊**，方向反了 ⇒ 我据此得出"OCR 无事可读"是错的。
2. 我 20 帧没碰到的形态不等于不存在（他 18:16 图与引擎 21:47 的 hit 都在那之后/之前发生）——**采样窗口太窄不能证否**，这条按"过滤会制造假缺失"处理。
3. 方案初稿把角区写成 `0.30W`，按参考图复核后胶囊左半边在区外，会被自己的贴边过滤丢掉 ⇒ 自查时改成 `0.40W` 并加"完整包含"判据。**动手前没先算区域覆盖，是同一类错**（先定阈值/边界再找证据）。
